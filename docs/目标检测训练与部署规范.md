# 智能实验室终端：目标检测训练与部署规范

文档版本：0.1.0（设计基线）

状态：待数据采集、模型训练和实机验收；本文中的性能数值是建议目标，不是已取得结果。

关联项目：智能实验室终端；AnchorDiff v0.6.1（本地基线提交 `e5d6798`）作为独立、版本化的外部算法依赖。

适用人员：数据采集与标注人员、算法开发人员、端侧部署人员、测试与运维人员。

## 1. 目的与边界

本模块从实验开始和收台后的图像中识别纳入管理范围的仪器，输出类别、置信度和位置框，为仪器位置变化分析提供观测数据。模块以成熟轻量目标检测模型的迁移学习为起点，不从零编写通用目标检测网络。

目标类别由实际实验室需要确定并可扩展，例如示波器、焊台、直流电源、信号发生器。上述类别是示例，不是限定类别清单，也不要求只能识别 4–6 类。电线、元件、纸张和个人物品默认不做逐项识别，其视觉变化由 AnchorDiff 的残余变化分析处理。

定位标记只用于图像几何定位与对齐。标记编号不得作为仪器资产编号，不通过在仪器上贴标记实现身份识别。检测器的 `label` 表示类别；检测出的两个示波器属于同一类，不代表系统已知道它们的序列号或实际资产身份。

检测模块不直接判断实验完成质量、电气安全或学生成绩。系统结合检测、位置匹配和残余变化，自动生成相对首次拍照的结果；教师后台只查看与导出。输入不可靠时系统输出“无法可靠判定”并提示重拍，不要求教师在后台修改算法判定。

## 2. 决策基线与接口要求

| 编号 | 要求 | 实现约束 |
| --- | --- | --- |
| DET-01 | 只识别配置中的仪器类别 | 类别表、类别 ID 与模型文件一起版本化 |
| DET-02 | 以本次首次拍照为位置基线 | 不依赖固定归位区；不把基线天然视为规范整洁状态 |
| DET-03 | 开始与结束图像使用同一坐标系 | 先对齐图像，再检测；比较使用同一固定有效矩形，框和掩膜不得混用全图与裁剪局部坐标 |
| DET-04 | 允许仪器位置大体不变 | 默认位置容差为 `0.1`，与检测置信度阈值分别管理 |
| DET-05 | 输出可追溯结果 | 保存模型、预处理、解码、配置版本及输入图像摘要 |
| DET-06 | 保留不确定性 | 遮挡、检测不稳定、超出支持范围不得强行生成“缺失”结论 |
| DET-07 | 训练、验证与部署可复现 | 固定环境、记录随机种子、数据分组与模型哈希 |
| DET-08 | 数据默认不进入 Git | 原始图片、身份数据、标注、模型权重和运行日志放在受控数据目录 |

AnchorDiff 使用的归一化中心位移为：

```text
d = distance(center_before, center_after)
    / max(sqrt(area_before), sqrt(area_after), 1)
```

其中面积来自同一坐标系中的检测框，单位为像素平方。`d <= 0.1` 表示落在默认位置容差内。`0.1` 不是 0.1 像素，也不是桌面宽度的 10%。例如面积为 10,000 像素平方的相同尺寸检测框，中心移动 10 像素时 `d = 0.1`。不同框尺寸会产生不同的允许位移。

该阈值会受检测框抖动和框尺寸误差影响。数据验证必须覆盖阈值附近的样本，不能仅报告目标检测 mAP。上线时不得为了提高通过率，自动放宽位置容差或悄悄更新本次基线。

## 3. 模型方案与选型方法

### 3.1 推荐起点

先选一个可合法使用、可以导出 ONNX、已具有 RK3588 部署参考实现的轻量 YOLO 模型，用实验室自采仪器数据微调。YOLO11n 是可评估的示例起点；也可选择已有更成熟 RKNN 工具链支持的轻量 YOLO 版本。模型版本应由精度、端侧延迟、工具链兼容性和许可证共同决定，不仅看参数量。

先在开发机上建立 PyTorch/Ultralytics 参考结果，再建立 ONNX CPU 参考结果，最后验证 RKNN。RK3588 用于端侧推理，模型训练主要在具有合适 GPU 的工作站上进行；没有 GPU 时可先完成数据整理、少量功能验证或使用获准的训练环境。

| 方案 | 用途 | 主要收益 | 进入条件 |
| --- | --- | --- | --- |
| 轻量检测模型 + bbox | 第一版产品 | 标注成本低，训练与部署路径较成熟 | 框定位足以支持位置容差和残余解释 |
| 更高输入分辨率或稍大模型 | 定位误差明显时的对照方案 | 可能改善小目标、相似仪器和框定位 | 实测收益超过额外延迟和内存成本 |
| 实例分割 | 第二阶段可选 | 仪器轮廓更精确，便于控制残余解释区域 | bbox 过度遮盖杂物或边缘差分成为主要问题 |
| 外观特征与同类拒配 | 同类多实例困难时的增强 | 降低同类仪器错配 | 先建立足够的同类交换、替换和遮挡测试数据 |

实例分割并非第一版必选。同样不能把 bbox 范围全部忽略，当成“杂物都已解释”：仪器框内可能存在新增线缆和物品。分割或保守边缘策略应有独立的残余变化对照评估。

### 3.2 模型许可与来源

使用前分别审查训练代码、导出工具、预训练权重、训练数据以及最终产品分发方式。Ultralytics 的开源与商业许可路径应依据所选版本的实际许可文件和官方说明确认；不能因为模型转成 ONNX/RKNN，便推定其许可约束消失。此项形成许可记录，不替代法律判断。

权重只从审核过的官方或授权渠道取得。终端默认读取本地权重，不自动从互联网下载；记录来源 URL、下载时间、许可版本和 SHA-256。不得加载来源不明的 Python pickle 类权重。模型授权、来源或完整性不明确时，不进入上线候选列表。

## 4. 数据采集规范

### 4.1 采集单元

数据的最小业务单元是一次受控拍摄场次或一次实验会话，包含开始图像、结束图像及必要的变化描述。用于训练的单图和用于业务验收的图像对分别建立清单，保留二者来源关系。

采集时覆盖实际可能使用的台位、摄像机、安装角度、仪器型号、光照和距离。不要只用同一台仪器、同一块桌面、同一天拍出的连续照片来代表真实部署范围。

建议记录以下去敏元数据：

```json
{
  "sample_id": "sample-000001",
  "capture_group_id": "capture-group-001",
  "session_group_id": "session-group-001",
  "station_group_id": "station-group-A",
  "camera_profile": "camera-profile-01",
  "view_profile": "rear-oblique",
  "split": "unassigned",
  "conditions": ["normal-light", "partial-occlusion"],
  "image_sha256": "<由采集工具计算>",
  "annotation_version": "annotation-v1"
}
```

这些 ID 是数据内部伪名，不包含真实姓名、学号、IP 地址或实际机房位置。若研究需要真实仪器实例的分组信息，另设受控的伪名 `instrument_instance_group`；该字段用于评估隔离，不表示产品已具备实例识别能力。

### 4.2 必须覆盖的场景

| 场景 | 采集内容 | 主要验证问题 |
| --- | --- | --- |
| 常规状态 | 不同仪器型号、显示屏亮/灭、实际支架和附件 | 类别识别与框定位 |
| 大体不变 | 重拍、轻微摆动、旋钮和线缆变化 | 框抖动是否造成“移动”或扰乱度虚高 |
| 真实移动 | 不同方向、不同距离、旋转 | 位置阈值与匹配能力 |
| 移入/移出 | 某类仪器出现或离开可见桌面 | 新增与缺失判定 |
| 同类多实例 | 两台同类仪器靠近、交换、遮挡 | 匈牙利匹配的歧义及拒配需求 |
| 干扰与负样本 | 包装、屏幕图片、非管理仪器、工具和空桌 | 假阳性与类别边界 |
| 光照变化 | 白天/夜间、局部阴影、反光、显示屏亮度变化 | 检测和差分的鲁棒性 |
| 成像问题 | 虚焦、运动模糊、曝光异常、镜头遮挡 | 质量门控是否拒绝错误输入 |
| 几何问题 | 小幅相机位移、标记缺失、标记误读、高物体视差 | 对齐误差能否被识别 |
| 未支持输入 | 新型号、极端角度、仪器超出画面 | 支持范围与不确定结果 |

采集尽量使用空场或同意参与的测试人员。镜头只覆盖必要桌面，避免拍到人脸、胸牌、学生姓名、屏幕账户和文件。展示样例与公开材料使用合成、重建或已去敏图像，不直接发布真实学生实验场景。

### 4.3 数据规模与停止条件

第一批数据用于检查能否学到有效特征，数量由类别差异和现场条件决定。可从每类数百个有效标注实例起步，但这是采集规划量级，不是达到精度的保证。优先增加独立场次、仪器型号和困难样本，再增加同一视频中的相邻帧。

每次迭代按错误类型补充数据：漏检、同类误识别、框抖动、斜视、光照等。只有当分组验证集的关键指标趋于稳定，并且外部台位测试达到门槛，才停止扩充；不能仅以训练损失变低为结束依据。

## 5. 标注规范

### 5.1 类别定义

建立 `class_catalog`，每类包含稳定英文机器标签、中文显示名、包含/排除规则、正反例、类别 ID 和版本。例如 `oscilloscope`、`soldering_station` 仅为示例；产品界面使用中文名称，数据和接口使用稳定机器标签。

焊台的主体、支架和烙铁可能分散。第一版建议把“焊台主体”作为目标检测单元，在类别定义中说明哪些附件不纳入框；附件是否归整由残余变化表达。若把附件一起纳入大框，容易使几何中心随摆放变化，不利于 `0.1` 位置容差。该决策由真实图像对实验确认后固定。

### 5.2 bbox 规则

1. 标注仪器主体的可见外轮廓轴对齐包围框，避免包含很长的连接线或手臂。
2. 对部分遮挡目标，采用统一的“可见轮廓框”或经核实的“完整主体框”政策；二者不得混用。第一版优先选择可见主体框并记录遮挡等级，业务端对明显遮挡门控。
3. 完全遮挡的仪器不凭记忆画框；该样本保留“无法观测”的质量标签，不能用来证明仪器缺失。
4. 出画目标记录截断标签。位置比较端应拒绝会影响归位判断的严重截断样本。
5. 同类多个可见实例逐个标注。所有纳入范围、足够可见的目标均标注，不能遗漏后又作为背景训练。
6. 负样本对应空标注文件。难以确定类别的目标进入待核实清单，不随意标成背景。
7. 遮挡/模糊等附加标签单独保存在受控清单中；标准 YOLO 检测文本本身不携带这些质量字段。

YOLO 检测标注格式为 `class_id x_center y_center width height`，坐标相对原图宽高归一化到 0–1。导入前校验类别范围、框宽高、坐标边界、图像尺寸和重复框。

### 5.3 标注质量检查

每批由另一名人员抽查标注，错误集中时扩大抽查或重标整批；困难场景全量复核。记录争议原因与规范修订，不只修单张图。对同一张图的双人标注计算类别一致性和框 IoU，用于发现定义差异；该数值是标注一致性，不是模型精度。

标注规范发生实质变化时，更新版本并重新检查受影响的数据。禁止新旧框定义混合训练后仍沿用同一个数据版本号。

## 6. 数据划分与泄露防护

### 6.1 分组后再划分

训练、验证、测试以拍摄场次或实验会话为最小隔离组。同一原始图片的裁剪、增强、不同格式、视频邻帧、开始/结束图像必须进入同一划分。数据增强只应用于训练集。

建议初始比例约为训练 70%、验证 15%、测试 15%，可依据独立场次数和类别分布调整。比例不是硬性验收标准；独立性和代表性优先。记录具体随机种子、划分算法、组数、图数和每类实例数。

同时保留两种评估：

- **已知部署条件测试**：测试集与训练集属于预期支持的台位/型号范围，但拍摄会话独立，用于验收日常运行表现。
- **外部条件测试**：保留未参与调参的台位、安装位置或仪器实例组，用于估计迁移表现。未达到门槛时明确不支持相应条件，不能把结果与常规测试混成一个平均值。

若某些样本共享原图、视频、会话或连续拍摄来源，用连接关系合并为不可拆分组后再划分。若要求某台位完全留出，应在组级别整体留出，而不是随机抽取该台位的单张照片。

### 6.2 测试集封存

测试集不用于选择模型、输入尺寸、置信度、NMS 阈值、位置容差或 INT8 校准。验证集用于调参；最终候选只在已封存测试集上按预先登记的协议评估。

发现测试错误后可以决定下一版本需补充哪些场景，但不得反复针对相同测试样本优化并声称该测试仍是独立验收。新一轮开发应保留旧结果并建立新的独立测试批次。

执行文件 SHA-256 精确去重和感知相似性检查，对跨划分的疑似近重复进行人工确认；保留去重报告。不让测试数据进入训练缓存、主动学习队列或量化校准清单。

## 7. 训练流程与示例

### 7.1 环境与数据目录

训练工具依赖锁定在专用训练环境中；终端运行环境与训练环境分开维护。训练前保存 Python、框架、CUDA/驱动（如适用）、模型和依赖版本，确认所选版本满足当前硬件及导出要求。

建议目录以下均为本地受控数据，不提交 Git：

```text
local_data/
  instruments_v1/
    images/train/
    images/val/
    images/test/
    labels/train/
    labels/val/
    labels/test/
    private_manifests/
local_models/
runtime/model_runs/
```

仓库只保存去敏类别规范、配置模板、训练脚本、测试脚本及数据版本摘要。实际 `dataset.yaml` 可包含本机路径，应生成在受控目录，避免发布机器目录结构。

下面是配置示意，路径和类别表必须替换成实际数据；示例中的两类仅演示文件格式：

```yaml
path: <本机受控数据目录的绝对路径>
train: images/train
val: images/val
test: images/test
names:
  0: oscilloscope
  1: soldering_station
```

### 7.2 微调示例

以下命令依赖事先安装并锁定版本的 Ultralytics，以及已核实许可的本地预训练权重。`local_models/yolo11n.pt` 只是示例文件名，命令不会凭空产生这些数据或权重。PowerShell 中可单行执行：

```powershell
yolo detect train model=local_models/yolo11n.pt data=local_data/instruments_v1/dataset.yaml imgsz=640 epochs=100 batch=8 seed=42 project=runtime/model_runs name=detector_v1
```

`epochs=100`、`batch=8`、`imgsz=640` 是初始实验参数，不是最佳配置。训练期间使用验证集观察每类漏检和框定位，保存训练日志、实际超参数、最佳检查点与最后检查点。随机种子有助于复现，但 GPU 算子和工具链可能仍非完全确定，必须记录实际环境。

增强从实际扰动出发：适度亮度、对比度、颜色和小幅几何变化。夸张旋转、镜像、强透视和裁剪应有现场合理性；避免把物理上不可能的仪器形态变成主要训练数据。训练增强不能代替真实光照、真实斜视和新型号采集。

### 7.3 验证与模型选择

```powershell
yolo detect val model=runtime/model_runs/detector_v1/weights/best.pt data=local_data/instruments_v1/dataset.yaml split=val imgsz=640
```

选择模型时同时看每类 precision、recall、mAP50、mAP50–95、误检类型、框中心误差和业务位置判定。不能用一次聚合 mAP 抵消某个关键仪器类别的持续漏检。

只有在锁定模型、预处理、阈值和业务规则后，才运行最终测试：

```powershell
yolo detect val model=runtime/model_runs/detector_v1/weights/best.pt data=local_data/instruments_v1/dataset.yaml split=test imgsz=640
```

每次实验建立登记项：数据版本、划分版本、代码提交、模型配置、初始化权重哈希、训练参数、验证结果和是否进入候选。不得凭训练命令成功便称“模型已经可部署”。

## 8. 对齐、预处理与坐标规范

### 8.1 推荐应用链路

```text
开始/结束原始图像
→ 图像质量与标记可用性检查
→ 镜头畸变校正（已标定时，两图一致）
→ 将结束图像对齐到开始图像的基线平面
→ 验证已冻结固定矩形 ROI 的全部像素有效及几何质量
→ 从两张同坐标图像裁出相同的固定比较矩形
→ 在两张比较图上分别检测
→ 还原模型输出到同一比较图的 baseline_registered_pixel 像素坐标
→ 调用 AnchorDiff 做匹配与残余分析
→ 在固定 ROI 比较图上绘制解释框和残余区域
```

对齐之后检测是当前集成的关键约束。AnchorDiff v0.6.1 的配对分析会变换图像，但不能假定它同时变换应用传入的最终检测框或掩膜。应用应先完成对齐，并防止调用时重复应用几何变换；外部对齐的参数、误差与有效 ROI 仍需在业务记录中保存。

固定 ROI 随相机配置/本次基线冻结，记录裁剪原点与输出宽高。最终固定 ROI 比较图直接命名为 `baseline_registered_pixel`，其左上角为 `(0, 0)`；首次基线标准 frame 从建立时就是经过有效性检查的该裁剪图。开始与结束使用完全相同矩形，不能按每次结束图像的有效范围动态缩小或平移 ROI，否则面积比例和对象位置失去可比性。变换后该固定矩形内有无效填充像素、缺失区域或不满足覆盖条件时，应用拒答并提示重拍；不通过将黑边当作桌面来继续评分。

AnchorDiff v0.6.1 的残余差分面积比例分母是传入比较图的整幅像素数，未提供任意有效掩膜下的有效面积分母。第一版因此以经过有效性检查的固定矩形裁剪作为完整比较输入。检测框、掩膜、残余区域进入 core、归档和叠加时均使用同一 `baseline_registered_pixel` 坐标，不另保留名称相同的全图坐标。原始 `camera_pixel` 到比较图的复合变换记录包含去畸变参数、warp 及裁剪 offset；不能将原始相机框或未裁剪全图框直接传给 core。未来若支持不规则有效掩膜及有效面积分母，须发布新的算法/配置版本，重新验收，不沿用本版分数含义。

对几帧连续照片，先挑选合格帧，再对被选中的实际帧检测。不能把另一帧的框直接复用到所选图像，也不能向整段序列传同一套结束检测结果。

斜视下，桌面单应性不能消除高仪器的全部视差。摄像机发生移动时，仪器上表面可能相对桌面标记产生假位移。因此应优先固定相机、避免安装结构晃动，并以真实高仪器测试界定允许相机运动；不能凭桌面标记重投影误差低就宣布所有仪器已准确对齐。

### 8.2 输入约定

内部图像建议统一为 `H × W × 3`、RGB、`uint8`；相机输出的 BGR/YUV 由采集层显式转换。每个模型适配器根据其框架要求转换，不假定所有库对 NumPy 图像都按 RGB 解释。用红/蓝色块夹具检查通道顺序，用非正方形图像检查宽高顺序。

统一显式记录模型宽高，如 `model_width=640`、`model_height=640`。接口中约定 `image_shape=(height, width)`，避免将 `input_size` 的宽高解释混淆。AnchorDiff 现有适配器对输入尺寸和直接 resize 的行为应通过实际测试核实，尤其非方形输入。

对于 YOLO 常见的 letterbox 预处理，记录缩放和填充：

```text
r = min(model_width / image_width, model_height / image_height)
new_width  = round(image_width × r)
new_height = round(image_height × r)
pad_left、pad_top = 实际使用的左、上填充值
```

解码后逆变换为：

```text
x_original = (x_model - pad_left) / r
y_original = (y_model - pad_top) / r
```

填充舍入、是否拉伸、是否除以 255、输入 layout、插值方法和颜色顺序必须与训练/参考推理一致。框还原后裁剪到有效图像范围，再转换成 `x, y, width, height`。不得把归一化模型坐标直接当原图像素，也不得只逆变换 bbox 而遗漏实例掩膜。

## 9. 导出与 ONNX 验证

### 9.1 导出示例与版本约束

先选择 RKNN-Toolkit2 当前版本明确支持的 ONNX 算子与 opset，再锁定导出参数。下面给出一个静态输入、原始输出的示意命令；`opset=12` 仅为可验证起点，不保证适用于每个模型或工具链：

```powershell
yolo export model=runtime/model_runs/detector_v1/weights/best.pt format=onnx imgsz=640 opset=12 dynamic=False simplify=False nms=False
```

记录导出工具版本、输入/输出名称、shape、dtype、opset 和模型哈希。ONNX 图能被加载只证明格式可读，不证明预处理、解码或业务效果正确。

### 9.2 模型专用后处理

不同 YOLO 版本和导出方式可能返回 `[1, 4+classes, candidates]`、多尺度特征图或已完成后处理的结果。不能根据“YOLO”名称套用一个固定输出假设。通过模型元数据、官方实现和实际输出共同确认：框是 `xywh` 还是 `xyxy`，分数如何组成，是否含 objectness，是否需要 sigmoid、DFL、anchor/grid 或 stride 解码。

处理顺序固定为：原始 head 解码 → 类别置信度计算 → 置信度过滤 → 按约定执行 NMS → letterbox 逆变换 → 图像边界检查 → 类别 ID 映射 → 统一 `Detection` 输出。记录 NMS IoU 阈值、是否按类别抑制、最多保留框数以及同分时的排序规则。训练/ONNX/RKNN 的后处理尽量共用代码。

AnchorDiff v0.6.1 的 ONNX/RKNN 默认解码器只面向行式 `[x0,y0,x1,y1,score,class_id]` 输出，不能直接解释原始 YOLO head；现有直接 resize 预处理也不等于 letterbox。实际接入可在本项目实现符合 `Detector.detect()` 协议的完整适配器，再传给 AnchorDiff，不要求修改独立公开算法仓库。

### 9.3 一致性门槛

在固定验证夹具上对比参考模型与 ONNX：输入张量、输出 shape、检测类别、中心坐标、框 IoU、置信度和漏检。夹具必须包含非方形图、边缘目标、负样本、同类近邻、重叠框和通道检查图。

对于阈值附近的数值差异，区分浮点误差与后处理错误。建议初始回归门槛：高置信匹配目标中心误差中位数不超过有效图像对角线的 0.2%，且典型目标框 IoU 不低于 0.98；这是转换一致性目标，应按具体模型和有效图像尺寸调整、冻结并留档，不能当作真实标注精度。

ONNX 验证失败时先修坐标、预处理与解码，不通过重新训练掩盖软件错误。

## 10. RK3588 / RKNN 部署规范

### 10.1 工具链分工

模型转换在符合 Rockchip 官方支持条件的主机环境进行，运行在 RK3588 开发板。板端系统、NPU 驱动、RKNN runtime 与转换工具版本按厂商兼容要求固定。Windows 开发机可使用合适的受支持 Linux 环境转换，不承诺 Windows 本机可直接执行所有 RKNN 工具。

先进行非量化或工具链支持的较高精度转换对照，再评估 INT8。使用 Rockchip 对应模型参考实现作为解码依据，但必须核对其模型结构、类别数和导出版本与本项目相同。

AnchorDiff v0.6.1 的默认 RKNN runtime 构造代码需要核对实际包 API；常见板端 API 类名为 `RKNNLite`。建议应用自己构造已验证 runtime 并实现检测适配器，或按所用版本修正适配方式。不能将安装某个可选依赖等同于“上板即用”。

### 10.2 INT8 校准

校准图像仅从训练分组或预先单独划出的训练校准分组选择，不使用封存测试集。覆盖实际光照、仪器类别、背景和空场，避免只选择正常明亮图片。清单记录图像哈希、分组和预处理。

校准样本量根据官方工具要求和验证曲线选择；可从数百张有代表性的训练图像起步，但不能把这个量级当作充分性证明。确保校准与推理使用一致的颜色、缩放和归一化策略，防止工具链配置与应用层重复除以 255 或重复减均值。

INT8 模型通过后，重新评估检测和图像对业务指标。建议转换回归门槛：相对参考模型的 mAP50–95 下降不超过 0.02（绝对值），每类 recall 下降不超过 0.03，仪器错误“缺失”率增加不超过 0.01。若不满足，排查校准分布、算子与量化敏感性，再评估更高精度方案；这些数值属于初始验收建议。

### 10.3 端侧运行检查

| 检查项 | 要求与证据 |
| --- | --- |
| 完整性 | 启动验证本地模型和类别文件哈希，缺文件或不匹配则不启用判定 |
| 输入 | 核实 NHWC/NCHW、RGB/BGR、uint8/float 与实际 RKNN 模型一致 |
| 输出 | 保存去敏的 shape/dtype 诊断，模型不兼容时返回结构化错误 |
| 坐标 | 在基线坐标图上叠加，框不漂移、不转置、不按原始结束图误绘 |
| 内存 | 记录模型加载、单次推理和连续运行内存，异常可恢复 |
| 延迟 | 分别记录采集、质量检查、对齐、检测、差分及总耗时 |
| 热稳定 | 在实际机箱、供电和散热条件下测连续运行温度与节流 |
| 断网 | 本地模型和规则完整可用，结果进入本地待同步队列 |
| 失败恢复 | runtime 失效可重建；重试有上限，失败会话可重拍 |
| 版本回滚 | 新旧模型原子切换，失败恢复到已验收版本，不混用类别表 |

当前没有 RK3588 实测数据。按《开发实施计划》的统一建议基线，合格输入条件下“收台拍照至结果显示”p95 不超过 5 秒，以选定摄像机分辨率、输入尺寸、板卡和 UI 负载完成至少 200 次端到端测量，并完成连续 8 小时运行。NPU 的标称算力不能替代端到端实测。

### 10.4 端侧判定与服务端归档

默认由受管终端 worker 完成采集、推理和判定，断网时保存结果和证据到本地待同步队列。服务端校验受管设备身份、worker 来源、输入/模型/配置摘要、schema 与允许的版本组合，随后归档原始结果；教师浏览器不直接提交或修改判定结果。

哈希证明文件内容一致，不独立证明结果由可信 worker 生成。设备注册、受控凭据和经认证的传输用于来源校验，哈希用于数据关联与完整性检查。同步结果携带 `attempt_id`、`backend_id`、软件/模型版本和输入摘要，重复同步按幂等键返回同一归档记录。

服务端复算仅作为可选验证任务，创建独立 `attempt` 并标注所用 backend，不能覆盖端侧原判定。CPU、ONNX 与 RKNN 可能出现浮点或量化差异，不假定结果逐位一致；根据预先冻结的转换与业务一致性门槛比较，差异保留在审计记录中。

## 11. 统一检测接口与质量拒答

### 11.1 对 AnchorDiff 的输出

统一结构为 `Detection(label, bbox, confidence, mask=None)`；bbox 使用最终固定 ROI 比较图的 `baseline_registered_pixel` 像素 `x, y, width, height`，原点是该图左上角 `(0, 0)`。mask 若存在则为该比较图全幅布尔掩膜。core 输入、归档对象、残余区域和叠加输出使用完全相同坐标，不在归档时另加 ROI 原点。

```json
{
  "label": "oscilloscope",
  "bbox": [320.0, 180.0, 240.0, 160.0],
  "confidence": 0.93
}
```

适配器验证 `confidence` 在 0–1、坐标有限、宽高为正、类别合法，不接受 NaN 或非法类别 ID。模型异常与“没有检测到对象”分开返回，不能把推理失败转换成空列表。

业务外围另保存检测诊断：模型哈希、阈值、候选数、各阶段耗时、有效 ROI、图像质量、检测稳定性及错误码。不要给 AnchorDiff 伪造额外构造参数；附加业务元数据放在本项目封装层。

### 11.2 不确定输入的处理

以下至少进入重拍或 `needs_review`，不输出有把握的归位结论：

- 图像模糊、曝光异常、有效 ROI 过小或无法可靠对齐。
- 定位标记不足、配置不一致、强相机运动或高物体视差超出验证范围。
- 手部/人体或遮挡物覆盖仪器关键区域，目标严重出画。
- 原本可见仪器在结束图中未检出，但存在低置信候选、严重遮挡或多帧不一致。
- 同类多实例无法可靠对应，疑似同类替换或高成本强行匹配。
- 模型未支持的类别/角度、推理失败或输入输出契约不一致。

检测器置信度不是“仪器确实在场的概率”。某目标没有检测框，也不能单独证明它不存在。若采用低/高双阈值，高阈值用于可靠候选，低阈值候选保留供不确定性检查；两者通过验证集校准，不与位置容差 `0.1` 混用。

AnchorDiff v0.6.1 对传入的任何置信度低于 `0.60` 的 Detection 会触发检测置信度门控。因此低置信候选保存于本项目应用层，先用于漏检、遮挡和不稳定检查，不直接与可靠 Detection 一起传入 core，否则会使原本可分析的场次整体拒答。若应用配置可靠阈值低于 `0.60`，应在版本兼容校验时拒绝该配置，或以新算法版本明确重新定义门控；不得篡改/抬高原始置信度绕过门控。原始推理失败始终为结构化错误，不能转换成“成功但空检测”。

可对每次拍照采集短帧组，并比较对象检测的类别、框位置与数量稳定性；这用于筛选可靠输入，不意味着必须实时视频跟踪。多帧策略改变后，重测拒答覆盖率和完整业务指标。

现有 AnchorDiff 已有部分图像与检测置信度门控，但并未完整实现上述手部遮挡、标记缺失、空检测和强运动策略。本项目需要补充并验收，不能仅在界面文案中声明已支持。

## 12. 测试指标与验收计划

### 12.1 分层评估

| 层级 | 主要指标 | 数据与解释 |
| --- | --- | --- |
| 检测 | 每类 precision、recall、mAP50、mAP50–95 | 独立分组单图测试；报告样本数和困难场景 |
| 定位 | 中心归一化误差、框 IoU、静止重拍框抖动 | 标注框及固定位置重复拍照 |
| 配对业务 | `stable/moved/missing/new` 的混淆矩阵与宏平均 F1 | 独立图像对；同类多实例单独报告 |
| 误报 | 在场仪器被判“缺失”的比例；稳定被判“移动”的比例 | 明确分母为真实在场/真实稳定对象 |
| 残余联动 | 仪器边缘误差残余、人工标注残余区域 IoU | 对照原图，确认没有遮掉新增杂物 |
| 拒答 | 不可判定召回、可判定覆盖率、覆盖率下的错误率 | 正常与困难输入均纳入，防止只靠大量拒答改善精度 |
| 转换 | PyTorch/ONNX/RKNN 检测与业务一致性 | 同一固定夹具及同一阈值 |
| 运行 | p50/p95 总延迟、分阶段耗时、内存、温度、异常恢复 | 选定实机、实际机箱和生产参数 |

位置边界测试覆盖 `d` 接近 0.1 的两侧，例如 0.08、0.10、0.12 附近，并记录真实移动、检测波动和最终判定。小旋转、框尺度变化和同类交换分别测试，不只平移单个理想矩形。

### 12.2 初始验收建议

下列指标仅为建议，在正式测试前冻结；尚未完成真实测试，不能用于宣传已有精度。统一验收基线以《开发实施计划》为准，本文件的训练/转换回归指标是补充检查，不取代统一业务门槛。

| 条目 | 初始建议门槛 | 限定条件 |
| --- | --- | --- |
| 支持类别识别 | 每类 precision、recall 均不低于 0.90 | 仅声明支持的可见条件，困难条件另报；0.95 可作为后续增强目标 |
| 在场误判缺失 | 对象级比例不高于 0.03 | 质量合格且真实在场的独立测试对象 |
| 稳定误判移动 | 对象级比例不高于 0.05 | 已定义允许扰动范围；阈值附近单独报告 |
| 配对状态判定 | 宏平均 F1 不低于 0.90 | 包括四类状态，不能仅报 stable 占多数的准确率 |
| 正常输入覆盖率 | 不低于 0.90 | 同时达到上述错误率；需报告全部拒答原因 |
| 严重质量问题 | 不可判定召回不低于 0.95 | 预定义模糊、遮挡、失标记、强运动测试集 |
| 端到端耗时 | 合格输入 p95 不高于 5 秒，至少 200 次测量 | 明确分辨率、模型、板卡、温度、并发负载和计时范围 |
| 运行恢复 | 连续 8 小时无无法恢复错误；故障注入后按规范恢复 | 使用实际机箱、供电、散热与业务负载 |

验收报告同时给出置信区间或分组 bootstrap 区间，抽样单位优先为会话而非相邻帧。稀有错误至少说明分母和样本局限；例如 300 个真正独立的试验中零次错误，单侧 95% 二项上界仍约为 1%，不能写成“错误率为零”。同会话内多个对象存在相关性时，不能机械套用独立二项结论。

合成样本只用于软件回归和故障注入，不替代真实场景验收。AnchorDiff 的已有合成测试通过也不证明本项目的仪器识别精度、相机安装效果或 RK3588 性能。

| T4 RKNN | RKNN 文件、校准清单、兼容版本表、板端测试报告 | 量化与端侧回归达到门槛，运行资源和恢复实测合格 |
| T5 业务验收 | 独立图像对结果、拒答报告、误报报告、端到端基准 | 冻结测试达到约定指标，教师只读，解释与图像坐标一致 |
| T6 发布维护 | 模型包、版本清单、回滚包、运维检查表 | 去敏审查通过，完整性校验和回滚演练完成 |

模型包至少包含模型文件、类别表、输入输出 schema、预处理/后处理配置、工具链版本、哈希、许可记录、支持范围和回滚说明。模型、类别表、解码器与阈值作为一个整体版本，不单独替换其中一项后沿用原验收结论。

模型卡包括：预期用途、禁用用途、数据采集范围、分组方法、训练环境、各条件测试结果、已知失败模式、隐私与许可信息、维护负责人和变更记录。负责人字段可在内部私有记录填写，公开模板不带联系方式。

## 14. 数据与安全管理

原始图像、标注、真实身份映射、训练缓存、模型权重和运行数据默认不提交 Git。仓库保存去敏模板和可复现流程；受控数据目录有最小权限、留存期限、删除记录和备份策略。预训练及最终权重体积不大也不改变该策略。

数据采集端避免记录真实用户身份，数据训练集不包含姓名、学号和账户信息。若图像含仪器序列号、网络配置、屏幕敏感内容，采集前遮挡或按可审计规则去敏；遮挡处理可能影响检测，应记录处理版本，避免在训练与产品推理间产生未说明的分布差异。

上传和读取图像设置大小、格式、像素总量与路径限制，拒绝路径穿越；不把用户文件名直接当存储路径。不在日志输出原始图像内容、完整身份或凭据。模型转换只处理可信模型，不对外开放任意模型执行接口。

更新候选模型经过离线验证，终端验证包完整性并原子切换。身份映射与算法数据分离，教师查看权限不包含模型更新、训练集导出或判定记录修改。导出的模型报告使用去敏字段，含 CSV 时转义以 `= + - @` 开头的文本字段，防止电子表格公式注入。
